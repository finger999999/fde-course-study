# 专题课 S2 · 本体引擎的工程实现

> **学习版说明**：内核怎么造。教材就是 `clife-onto-engine` 的源码和架构图本身——图上每个块都标了文件名，看不懂的地方打开代码。只上 S1 不上 S2，你能判断一个本体方案好不好，但说不出"好在哪一行"。

## 学习目标

- [ ] 用"判缝准则"判断一段代码该放内核、插件还是租户
- [ ] 复述 Action 引擎六步和三条内核铁律
- [ ] 说清 SPI 七槽位的正确用法（验收清单，不是自动化承诺）
- [ ] 知道两个 CI 门禁各守什么

## 题眼（全课最重要的一句话）

> **确定性边界置于模型之外：合法但违规的动作，在写后规则校验阶段被确定性回滚并留审计。**

这句话回答了客户真正担心的问题："AI 会不会绕过你们的规则？"——**答案是：它绕不过，因为边界不在它里面。**

## 一、三层切分与判缝准则

| 层 | 含行业词 | 内容 |
|---|---|---|
| **Kernel 内核**（机制） | **禁止**（CI 脚本强制） | 元模型、Action 内核、规则引擎、回滚、审计、置信度 |
| **Plugin 插件**（策略） | 是（隔离在插件内） | 五要素 Schema、映射、规则函数、Action handler、Agent、CQ |
| **Tenant 租户**（实例） | 是（实例数据） | 物理映射、实例数据接入、密级授权 |

内核与插件**只通过 SDK 通信——目录边界即红线**。"本体即基础设施"：内核只懂本体怎么运转，**不懂任何行业**。

**⭐ 判缝准则**：拿一段代码问——"**换成另一个行业（比如医疗），这段还成立吗？**"成立 → 内核；不成立 → 插件；涉及具体数字 → 租户。

## 二、⭐ Action 引擎：治理写的唯一通路

### 六步

```
1 guard 前置校验（参数 + 用户上下文 + 角色权限，不碰数据）
2 validate 预演（可选，跑全套但永不落库）
3 写入 overlay —— 写即可见
4 写后规则校验 —— declarative + function 两层，收集全部违反
5a 全过     → 异步 flush + 同事务落审计快照 + 副作用编排
5b 任一 hard 违反 → 确定性回滚 + 返回结构化拒绝
```

### 三条内核铁律

1. **写后判**：先写（到 overlay）再校验——操作系统的 syscall 校验的是"调用"，本体引擎校验的是"**世界**"（写完之后所有规则还成不成立）
2. **判全部**：收集全部违反，不是遇到第一个就短路
3. **拒绝是数据**：连"没权限"都返回结构化的 Violation 而不是抛异常——**在这个内核里，"拒绝"是一等公民的返回值**

### Action ≠ 普通 tool calling

| | 普通 tool calling | **Action** |
|---|---|---|
| 谁决定成不成立 | 模型决定调什么就执行什么 | **模型只能"申请"，引擎决定成不成立** |
| 失败长什么样 | 异常 / 一句报错文本 | **结构化拒绝** |
| 留痕 | 看实现心情 | **强制审计快照（成功和被拒都有）** |

**一句可以拿去用的话术**：客户问"你们的 AI 会不会乱改数据"——**"Agent 只能申请，引擎决定。而且它申请的每一次，无论成败都有快照。"**

### validate 预演给谁用（跑全套但永不落库）

- **前端**：让用户在点提交之前就看到"这么填会被拒"
- **Agent**：先试一次，避免拿真实拒绝当学习信号
- **FDE**：调规则时不用反复清数据

## 三、SPI 七槽位：接一个新行业要交的七样

插件接口（SPI）定义了七样东西，**但注意：实测编译产物只覆盖其中五格**（两格完全不生成，两格只出骨架，一格格式不匹配）。

> **七槽位的正确用法：它是验收清单**（插件齐不齐，照这七格逐个点）**，不是自动化承诺。**
> 这张表本身就是"别信文档，去看代码"的活教材。

## 四、CI 两个门禁：守住"换行业零改内核"

| 门禁 | 执法方向 | 一句话 |
|---|---|---|
| `check_kernel_purity.py` | **反向**：内核源码禁止出现任何行业词 | **一个二十行的脚本，守住了整个产品的可复用性** |
| `check_plugin_capabilities.py` | **正向**：插件声明的能力与实现必须对齐 | 防止插件声称能做实际没做的事 |

### ⭐ 可以脱离本引擎复用的一条方法论

**任何一条纪律，问一句："它能被一个脚本检查吗？"** 能 → 固化成 CI，零人力永不疲劳；不能 → 它现在还停留在"靠自觉"。（第八课的"固化三问"在这里的工程形态。）

## 五、补章：记忆内核四层（token 预算即架构）

智能体的记忆不是"越大越好"，而是**分四层、各管各的预算**。超了不会报错——**只是慢慢变笨**：关键规则被挤出注意力窗口，输出质量悄悄滑坡，而你找不到任何报错日志。

| 层 | token 预算 | 放什么 |
|---|---|---|
| **CRITICAL** | 150–200 | 违反就出事的红线（安全、合规、禁令） |
| **RULE** | 300–500 | 行为规范、输出格式、工作流程 |
| **CONTEXT** | 200–400 | 当前项目背景、客户口径、会话状态 |
| **BACKGROUND** | 100–300 | 参考知识、历史经验、低频备查 |

**classify.py 的归层逻辑**：行业相关内容**归插件层**，进 SPI 槽位⑤（Agent 定义），而不是塞进内核记忆——这与"判缝准则"是同一条纪律在记忆侧的投影。

**与 L3 渐进式披露是同一约束的两端**：L3 讲的是**生产侧投喂**（采集来的资料别一次全塞），本章讲的是**消费侧驻留**（常驻记忆按预算分层）。两端共用一个判据——"每次都要看还是可能要看"。

## 六、诚实边界（客户的技术负责人一定会问）

演示拦截效果时必须一起报边界：测试覆盖了多少样本、哪些路径还没验。**你先说，比被问出来强**——这本身就是第一课讲的"可信度从哪来"。

## 自测

1. 为什么规则在写入"之后"执行，而不是之前？（校验的是"世界"不是"调用"）
2. "拒绝是数据"是什么意思？为什么重要？
3. SPI 七槽位为什么不能当自动化承诺用？
4. 两个 CI 门禁各守什么方向？
5. 记忆四层各管什么？超预算会怎样？（CRITICAL/RULE/CONTEXT/BACKGROUND 各有 token 预算；不报错，只是慢慢变笨）
