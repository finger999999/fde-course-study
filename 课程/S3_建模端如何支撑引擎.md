# 专题课 S3 · 建模端如何支撑引擎（studio-ontology）

> **学习版说明**：S2 讲了引擎内核怎么造，S3 讲怎么给它"编译应用"——那么严格的一套内核，怎么才能在几天之内为一个新行业填出插件？答案在建模端。读完 S1→S2→S3，第五课（亲手用工具产出插件）就是水到渠成。

## 学习目标

- [ ] 说清为什么必须有建模端（为什么不能直接手写插件）
- [ ] 画出"两仓一条流水线"，知道 IR 存在的全部理由
- [ ] 理解那个强制停点 ⏸ 为什么必须存在
- [ ] 区分"设计上的克制"与"能力上的边界"

## 一、为什么要有建模端

S2 的内核很严格——严格是好事，但**严格的东西通常也难填**。直接手写插件有三个结构性问题：

1. **手写的前提是"你已经知道要写什么"**——而新项目一开始你恰恰不知道
2. **业务专家看不懂 Python**——规则要业务方确认，但他们读不了代码
3. **手写没有一致性保证**——十个人写出十种结构

> **所以中间必须有一份业务专家能读、能改、能确认的东西——这就是 IR（中间表示）存在的全部理由。**

## 二、两仓一条流水线

```
astra-studio（建模工作室，另仓）          clife-onto-engine（运行时内核）
┌─────────────────────────────┐        ┌──────────────────┐
│ ① 业务分析（Intake 契约）     │        │                  │
│ ② 五要素 IR 七段             │  编译   │  插件包           │
│ ③ 编译产物 + 人工收尾         │ ─────▶ │  （引擎加载执行）  │
└─────────────────────────────┘        └──────────────────┘
```

**这个工具最聪明的地方**：它没有让业务团队学一套新语言，而是**站在业务团队已经会的 DDD 上，做一层翻译**（DDD 概念 ↔ 五要素有对照表）。你在客户现场做的事件风暴，不是白做的中间品——**它就是编译器的输入**。

### IR 七段与 ★FDE 核心

IR 共七段（对象 / 关系 / 函数 / **规则** / 动作 / 数据来源 / 能力问题 CQ），其中 **§4 Rules 段标着"★FDE 核心"**——业务规则是整套本体里最值钱、也最需要人判断的部分。

## 三、⭐ 四命令与唯一的强制停点

| 命令 | 干什么 | 强制人审 |
|---|---|---|
| `map` | 业务分析 → 七段 IR | 无 |
| `compile` | IR → 插件骨架 | 无（已存在不覆盖，只告警） |
| `validate` | 四段校验 | 无（只诊断） |
| **`model`** | **map → ⏸ 你审 IR → compile** | **★唯一有强制停点** |

### 停点审四项

对象边界 / 关系语义 / **规则的 severity·backing·出处** / Action 的写入与人工介入点。**你可以直接改 md 文件再继续。**

> **那个 ⏸ 为什么必须存在？因为本体是治理的锚点——一份没有人确认过的治理基准，不是治理基准。**

**另一处"权限即职责"的设计**：`validate` 校验器**无权改代码**——它只能告诉你哪里不合格，不能替你抹平。这是"纪律靠机制不靠自觉"的又一个干净例子。

## 四、⭐ 诚实边界（本课最值钱的一节）

编译产物不是成品。机器负责把结构立起来，**人负责把判断填进去**：

- **function 规则的函数体、Action 回写逻辑、参考数据**是 FDE 的手艺活——产物里用 `TODO(FDE)` 和 `NotImplementedError` **显式标注**
- 一个项目留了 121 处 `NotImplementedError`——**这不是没做完，是明确划出"机器到此为止、人从这里接手"的界线**
- **一个不敢留 NotImplementedError 的 FDE，会让模型把它猜的业务规则写成看起来能跑的代码——那才是灾难**

**两个必须分清的概念**：

| | 含义 |
|---|---|
| **设计上的克制** | 刻意不自动生成（规则体留人填），因为判断必须人来出 |
| **能力上的边界** | 工具暂时做不到 |

另外要知道的结构性事实：**IR 七段只覆盖 SPI 七槽位中的五格**——那两个 ❌ 是**结构性缺口**，不是"待补功能"。验收标准：编译产物的五要素与手写插件**同构**。

## 五、⚠️ 两仓红线

- 业务数据/名录**不许写进插件仓**（真实数据走租户目录）
- 引擎与插件只通过 SDK 通信，**目录边界即红线**

## 六、S1→S2→S3→第五课的关系

| 课 | 回答什么 | 给你什么 |
|---|---|---|
| **S1** | 本体**是什么**、为什么必须有 | 判断力 |
| **S2** | 引擎**怎么造**（运行时端） | 骨架认知 |
| **S3** | **怎么给它编译应用**（建模端） | 那把工具，以及它的边界 |
| **L5** | **亲手用那把工具**，产出能在引擎上跑起来的插件 | 手艺 |

> 只上一门的话，上 S1——工具会换，那套判断不会。
