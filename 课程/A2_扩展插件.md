# 专题课 A2 · 扩展插件：拆透 fund-review，学会写自己的

> **学习版说明**：四级台阶的第三级——写自己的插件。教材是一个真实的垂直插件 `fund-review`（采购报价优化，54 个文件）全仓读码。它证明的不是"这个插件多厉害"，是"**这套工具链能造出这种量级的东西**"——它就是你的未来样本。

## 学习目标

- [ ] 说清一个插件的骨架（Plugin Structure）由哪几类文件构成
- [ ] 理解"红蓝对抗"设计，以及最见功力的一处细节
- [ ] **掌握可迁移判据：这一步能不能写成脚本？能，就别交给模型**
- [ ] 理解 Plugin Traits 是"观察"不是"配置"

## 一、fund-review 是什么

一个"Vertical Plugin"（垂直插件）：针对一类具体业务（报价优化 + 预审），包含 **38 个脚本（其中 12 个扫描器）、4 个 skill、2 个 agent、4 个命令、5 个参考文件**。四个 skill 串成一条流水线：解析 → 扫描 → 研判 → 出报告。

## 二、⭐ 红蓝对抗（两个站在对立面的 agent）

一个 agent 负责"优化报价"，另一个负责"预审挑刺"——同一批材料，立场对立。

**⭐⭐ 最见功力的一处：两个 agent 都没有 Write 权限。**

> **好的角色设计不是靠嘱咐"你别乱改"，是让它想改也改不了。**（又是"权限即职责"：第二课工具权限、S3 校验器无权改代码，这里是第三次出现同一条思想。）

什么时候值得设红蓝：**当一件事有明确的对立立场，而且两边都有专业性的时候。**

## 三、⭐⭐ 但红蓝对抗不是这个插件的重点

数一下构成就会发现：**38 个脚本 vs 2 个 agent——这个插件的主体是确定性代码，不是大模型。**

### 12 个扫描器都在扫什么（举例）

| 扫描器 | 扫什么 |
|---|---|
| `scan_redundancy` | 跨工作簿/sheet 的重复内容 |
| `scan_caps` | 比例守恒（标准里的硬上限） |
| `scan_completeness` | 9 大费用科目缺失情况 |
| `scan_brand_models` | 设备品牌型号 ≥3（硬要求） |
| `scan_evidence` | 取值依据 |

⭐ **每一条都是"照规则一查就知道"的事**——品牌型号够不够 3 个、比例有没有超上限、科目缺了哪个。**这些交给脚本，因为它们不需要判断。**

### 那 agent 干什么

| 交给确定性脚本 | 才交给 agent |
|---|---|
| 12 类扫描、解析表格、公式引擎 | 从一堆发现里**挑出真正值得提的** |
| 重写表格、生成报告 | **排优先级**、用标准条款解释为什么 |

> **这就是"确定性优先"在插件层的活体：扫描是确定的，判断才是模型的。**

### ⭐ 给你的可迁移判据（做任何 AI 应用都成立）

> ### **这一步能不能写成脚本？能，就别交给模型。**

三个理由：① **确定性**——脚本每次结果一样，模型不保证；② **可测**——脚本能写单测，提示词不能；③ **成本**——脚本跑一万次成本不变，agent 跑一万次付一万次的钱。**模型是用来处理"规则说不清但人能判断"那一段的，不是用来做你懒得写的计算。**

## 四、插件的骨架（Plugin Structure）

一个插件 = `commands/`（命令）+ `skills/`（技能，含 SKILL.md）+ `agents/`（运行时专家）+ `scripts/`（确定性脚本）+ `references/`（按需展开的资料）+ 清单文件。

**Plugin Traits 是观察，不是配置**：你不"配置" trait——工具从你已经写下的东西里**推断**出来。比如 `expert-scoped` 这个 trait，就是"发现期专家"（A1 那种）和"运行时专家"（跟着插件跑在真实业务里的）的分界。
