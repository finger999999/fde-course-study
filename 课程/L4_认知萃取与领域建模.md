# 第四课 · 认知萃取 + 领域建模

> **学习版说明**：上半场学"零件"（业务分析六件套），下半场学"装配线"（把事件切成域）。这是把第三课的输入包变成可执行结构的一课——**FDE 的核心资产不是会用 AI，是把客户的模糊意图压成可执行的结构**。

## 学习目标

- [ ] 说清 `事件 → 画像 → 旅程 → 机会矩阵` 这条管线和它的先后顺序
- [ ] 分辨真画像和假画像，会给旅程选对场景
- [ ] 用 DDD 三判据切域，写对"业务事件"
- [ ] 知道跑完本课后路分三条，各自通向哪一课

## 上半场 · 认知萃取（产品设计这一栈）

### 核心管线

> **一条把"客户想要点什么"逼成可归域结构的方法论管线**：
> `事件 → 画像 → 旅程 → 机会矩阵` →（出口直接插进下半场的限界上下文）

### 五个方法（对应 insight 六件套）

| 方法 | 要点 | 工具 |
|---|---|---|
| **用户画像 Persona** | 按**行为/目标/动机/痛点**定义真实用户，不是人口属性堆砌 | `persona-insight` |
| **用户旅程图** | 五要素：用户 / 场景与目标 / 旅程阶段 / 行为·态度·情绪 / 机会点 | `journey-map` |
| **机会矩阵** | 把旅程暴露的痛点排优先级（影响 × 可行性） | `opportunity-brief` |
| **事件风暴** | 业务事件全量铺开再归簇，喂给限界上下文 | 下半场 `event-storm` |
| **产品思维** | 痛点/痒点/爽点；点线面体；用户体验五层 | 贯穿六件套 |

> **画像 → 旅程 → 机会矩阵是有先后的：画像不真，旅程就是编的；旅程不暴露痛点，机会矩阵就没有原料。这条顺序不能倒。**

### 三件必须讲透的事

**① 画像的真假之分（上半场核心）**：判据——两个画像如果目标、痛点、使用频率**没有显著差异，就不该拆成两个**。假画像按人口属性切（"25-35 岁白领"），真画像按行为差异切。

**② 旅程要选"最暴露痛点"的场景，不是最典型的场景**。选之前先回头看商业模式：收入线在哪条旅程上，就做那条。（反例 B-7：有项目旅程建模过重，返工。）

**③ 热点分层是给决策者看的，不是给自己看的**。P1–P5 的排序是价值判断——这正是"人的部分"不可外包给模型的具体落点。

**量级标尺（真实项目）**：102 个业务事件 → 16 簇 → 7 个画像（368 份问卷校准）→ 7 条旅程 → 5 条流程 → 10 个热点 → 7 个域。

## 下半场 · 领域建模（DDD 这一栈）

### 先把"事件"写对（最容易错的一步）

**事件是过去式的既成事实**——"材料已上传""质检已通过"；**不是**"支持材料上传""实现质检模块"（那是功能清单）。

> **判据**：能不能加"已"字、并且它已经发生过、不可撤销？能，才是事件。
> **事件写歪，域必然切歪，而且到第五课才会疼。**

### DDD 三件核心

| 概念 | 一句话 | 例子 |
|---|---|---|
| **统一语言** | 业务方和工程师用同一套词，且直接出现在代码里 | 同一个"老人"只有一个真相源 |
| **限界上下文** | 一个词在一个边界内只有一个含义；出了边界就是另一个概念 | 102 事件切成 7 个域 |
| **上下文映射** | 两域之间是"引用"还是"发布"必须说得出来 | 跨域一律 ref/发布，**不越界直写**（反例 B-8） |

### 切域三判据（对着你的域图问）

1. **同一个词在两个地方含义不同 → 该切开**（"老人"在照护域是被照护对象，在会员域是消费者——同一个人，两套属性、两套规则）
2. **状态机不共享 → 该切开**（生命周期在两处被不同的人推进，说明它其实是两个对象）
3. **能独立发布 → 该切开**（一个域要对监管机构负责，另一个对市场负责，捆在一起每次发布都要同时说服两边）

> **定义一个域最有效的方式，是说清它不管什么（`Does NOT own`）。**

### planner 五步流水线与你的角色

```
事件风暴 → 域模型 → 技能设计 → 骨架 → 填充
```

- 衔接靠**文件 + status.json**，不靠内存传参——管线是给你用的，不是替你做主的
- **跑到 `skill-map.md` 就停**（再往后是第八课的活）
- `Generic Capabilities`（通用能力）这段是精华：经常问"这个能力买现成的行不行？"答案常常是行——**不是所有域都值得当核心来建**
- **traits 是流水线的"分叉开关"**：现在选错，第八课生成的骨架就不对
- **skill-map 溯源自检**：每个插件都能在第三课的项目描述里找到出处；**找不到出处的插件，多半是你自己想出来的，不是客户要的**

## ⭐ 本课结束时必须知道：后面是分叉，不是流水线

```
domain-map ──▶ 第五课 本体建模（要"可执行的规则与闸"）
+ skill-map ──▶ 第六课 文档工程（要"可评审的文书"）
           ──▶ 第八课 技能插件（要"可发版的插件"）
```

**三条并行、不互为前置。** 交付模式决定优先级：模式二（赢单靠评审）→ 第六课优先；模式一（赢单靠能用）→ 第五+七课优先；要沉淀可复用能力 → 第八课。有真实项目没做本体建模，照样交出了完整可研——**别以为"不编译本体就不能写方案"**。

## 自测

1. 画像、旅程、机会矩阵为什么顺序不能倒？
2. 怎么判断一句话是不是"业务事件"？（能加"已"字、已发生、不可撤销）
3. 切域三判据是什么？
4. 你的 skill-map 里每个插件都能在项目描述里找到出处吗？
