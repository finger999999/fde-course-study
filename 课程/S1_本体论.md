## 一、我们缺少的不是数据，而是本体

有公司上了承诺"消灭数据孤岛"的大系统，结果差点把公司送进深渊——讽刺的是，他们的数据从来就不少。缺的是另一样东西：

> **谁依赖谁、谁触发谁、谁约束谁。系统记录了结果，没有记录"法则"。**

### ⭐ 字典 vs 物理引擎（本课第一个心智模型）

数据库像一本**字典**：它记录名词——"库存 500""订单状态：已发货"。但字典是死的，它不记录**物理定律**——"原料缺货 → 产线停产 → 订单违约 → 赔款"这条传导链，数据库里没有任何一行能告诉你。

> **数据是事实的存档，本体是现实的法则。没有法则，再多的事实也只是一堆彼此不相识的数字。**

**本体的核心价值，是让这些"活的规则"像数据一样被存储、被管理、被查询。**

## 二、本体在架构里的位置

### 幻觉的真正成因

大模型给的答案，外行读起来头头是道，内行读起来胡说八道。**这不是模型在概率上算错了，而是它根本没有接触过那条约束它行为的"业务规则"**——比如合同里写着"这类采购必须两人复核"，模型没撒谎，它只是不知道那条条款的存在。

所以防幻觉要靠**系统层面的确定性拦截**，不能靠 prompt 工程、不能靠模型的"理解能力"。商业场景不接受"我以为"。

### 四层架构：本体在 L3

```
L4 业务消费层     AI Agent · 业务应用 · 决策看板
                    ↑ 只通过本体接口交互，不直接访问底层数据库
L3 业务本体平台    Object（对象）· Link（关系）· Action（操作）
                    ★ 数据层和应用层之间的语义枢纽
L2 数据仓库/数据湖  结构化事实数据，但没有业务语义
L1 源系统          ERP · CRM · 生产控制 · IoT——割裂的、异构的
```

L3 不重新存储数据，它在数据之上建立**语义模型**：向下拉取 L2 的干净数据，向上为 L4 提供**受约束的操作接口**。

> **这个架构的重要意义：AI 看到的世界，是被本体层"翻译"过的世界——它看到的不是原始表，而是有名字、有关系、有规则的业务对象。**

数据中台做的是 L2 的事：管数据的流动，**不管业务的逻辑**。如果 AI 能直接写入系统而中间没有业务规则层约束它，出问题只是时间问题。

### 两条给架构师的原则

1. **业务规则应该是一等公民**——不是散落在代码里的条件判断，而是可以被查询、被审计、被 AI 读取的结构化资产
2. **AI 与业务系统之间需要一个中间层**——不是 prompt 模板，而是真实的业务语义模型，带约束、带权限、带写回能力

## 三、⭐ OAG 三层能力（缺一不可）

| 能力 | 回答的问题 | 缺了会怎样 |
|---|---|---|
| **操作发现** | Agent 怎么知道**能做什么**、参数是什么 | — |
| **执行约束** | 违规操作怎么被**实时拦截** | 只有发现没有约束 = 和让 AI 直连数据库一样危险 |
| **决策追溯** | 三个月后怎么回答"**为什么这样做**" | 出了事无法审计，没人敢负责 |

> **OAG 不是 RAG 的升级版，是 Agent 进入"写操作时代"的必要基础设施。**
> RAG 解决"从材料中找相关信息"（**读**）；OAG 解决"基于这些信息修改企业系统"（**改世界**）。
> GraphRAG 这类技术属于"读"的一边——它帮模型更好地理解实体关系，但不提供受治理的写回路径，挡不住"写错"。

## 四、AI FDE 为什么能 work

**大模型负责生成候选，本体负责收敛候选。** AI 生成得越快，如果没有收敛机制，污染也越快。AI FDE 之所以能 work，不是因为模型突然懂了企业，而是因为**它运行在一个已经把企业世界结构化的模型上**——这里的关键词不是 AI，是 Engineer。

### ⭐ 一句话记住四层分工

```
Harness（线束）      管循环——谁先跑、失败回哪步、重试几次
Ontology（本体）     管世界——有哪些对象、哪些规则算数、哪些能写回
Promotion Gate      管写回——什么结果允许落入正式系统
Memory Pipeline     管下轮怎么读——记忆怎么更新
```

**为什么这个分层重要**：出问题时你必须能判断是路由错了、规则错了、上下文拼错了、还是 Agent 输出错了。**层次混在一起，排查成本指数级上升。**

### 建模顺序铁律

**先建模、再看数据——顺序不能反。** 先看数据会被现有系统结构带偏，建出"系统长什么样"，而非"业务是什么样"。
